# 课堂视频计费、恢复与身份映射排查

日期：2026-10-24。以下区分官方计费规则、当前源码和本地模拟验证；未进行生产部署或声网账单验收。

## 为什么分享加老师视频会进入 2K

RTC 按接收者订阅的视频集合分辨率划档，Full HD 上限为 2,073,600 像素。

| 接收内容 | 集合像素 | 档位 |
| --- | ---: | --- |
| 1080p 分享 | 2,073,600 | Full HD |
| 1080p 分享 + 160×120 老师小流 | 2,092,800 | 2K |
| 1080p 分享 + 720p 老师视频 | 2,995,200 | 2K |
| 720p 分享 + 720p 老师视频 | 1,843,200 | Full HD |
| 720p 分享 + 160×120 老师小流 | 940,800 | Full HD |

因此，浏览器同时接收共享和老师摄像头，就足以进入 2K，并不要求服务端先合流。降低帧率或码率不能把上述分辨率档位直接降下来。[声网 RTC 计费策略](https://doc.shengwang.cn/doc/rtc/javascript/billing/billing-strategy)

项目中 `screenVideoPlan()` 原来直接返回所有共享大流和摄像头小流，绕过普通布局的接收预算；原默认共享为 1920×1080。这两个条件叠加，会在共享时突破之前设置的 Full HD 接收预算。

本次将课堂默认共享改为 1280×720，并让共享布局同样执行总预算：先共享、再可见摄像头小流，超预算画面暂停视频订阅，音频保留。非共享布局继续按焦点、可见面积和大小流分配。对于浏览器不支持小流而实际接收到更大画面的情况，依据 SDK 接收统计提高该路的预算成本并重新分配。统计驱动的纠偏有采样延迟，不能视为每一秒实际账单档位的绝对保证。

画质取舍：分享细小文字的清晰度低于原 1080p。若必须保留 1080p 分享，可以只订阅该路视频，老师保留音频或头像；另一种选择是降低到 900p 并预留摄像头额度，但必须把所有同时显示的摄像头一起纳入预算。当前实现选择 720p，保留老师视频及两路共享的预算空间。

## 拆分通道能否避免

- **同一频道内使用不同 UID 或不同发布客户端**：不会改变同一接收者订阅像素求和。项目已经用独立 UID 发布屏幕，仍会出现上述档位。
- **真正拆成两个 RTC 频道和两条接收连接**：可以改变各连接接收的流组合，但新增连接分别产生用量，可能还有音频、跨频道转发或录制费用。不能把“2K 分类消失”当成总费用一定减少。官方公开规则没有明确承诺该项目、套餐和身份组合的多频道聚合口径，应先确认合同口径，再做短时用量对照实验。本次未改为跨频道架构。[声网多频道接口与订阅说明](https://doc.shengwang.cn/api-ref/rtc/android/API/toc_channel)
- **发送端先把分享和老师合成一条流**：观众只接收一条受限画布时，可按该路订阅分辨率控制接收档位，但会失去独立老师画面、独立布局等能力，并需要实现真实的发送端合成；当前浏览器白板叠层不等于发送端合流。

## 录制和旁路推流另算

项目优先使用页面录制，`recorder-surface.ts` 选择画面，RTC 接收预算也适用于录制页面；录制输出默认 1280×720。源码仍有显式允许时使用的 `mix` 录制降级路径，其 `subscribeVideoUids` 是全部流。**将输出画布设为 720p，并不会自动限制录制输入源的集合分辨率**。本次没有宣称该降级路径的录制费用已被封顶。[声网单流和合流录制计费](https://doc.shengwang.cn/doc/cloud-recording/restful/overview/billing-strategy/billing)

如果业务另外启动旁路推流，声网推流服务器会作为接收者订阅大流，订阅费用与输出推流费用分别计算；仅调整输出合流画布也不能消除输入订阅费用。当前课堂修改没有新增旁路推流。[声网旁路推流计费](https://doc.shengwang.cn/doc/media-push/restful/overview/billing)

## 断网和后台恢复

原恢复逻辑主要修复缺失的轨道；SDK 保留旧轨道对象时，只调用播放可能继续显示冻结画面。返回前台时没有立即读取聊天，消息还可能等下一次退避轮询。RTM 初次失败后也缺少独立的重建重试。

本次处理：

1. `visibilitychange`、`online`、`pageshow`、窗口重新激活及网络类型变化合并触发恢复，避免同一次恢复重复执行。
2. 中止已挂起的快照与聊天请求，立即读取状态、字幕快照和消息；旧响应解析完后仍要检查请求代次。
3. 续期后按 SDK 当前远端用户清理离线参与者，重新建立远端音频和预算内视频订阅；单个音频恢复失败不会阻断其他画面。
4. RTM 异常时使用有上限的退避间隔重建连接，并在恢复后补齐消息和状态；轮询继续提供后备同步。
5. 分组教室在前台恢复及令牌即将过期时重新获取凭证。离开、结束课程时取消恢复或忽略过期结果。
6. 系统已结束屏幕采集时清除本地共享状态。浏览器安全限制要求老师再次点击共享，不能静默重新打开系统选择器。

## 名字串位及同账号多设备

排查确认了三种可复现的代码风险，不代表已经从生产日志确认截图的唯一成因：

- 身份匹配把显式连接 UID 与旧版账号哈希放在一次 `find()` 中，较早成员的旧映射可能抢先匹配；现在先在整个名单中找显式连接，只有旧版缺失字段时才使用哈希回退。空 UID 列表代表已离线，不再触发旧版回退；冲突映射不绑定到具名席位。
- 画廊、白板和录制原本可能分别选中同账号不同设备的主摄像头；现在共享同一选择规则，每个账号只显示并订阅一路主摄像头，优先有视频的连接，同等条件下优先本机并稳定排序。明确开启的辅助摄像头独立保留。此规则没有禁止同账号登录多个设备，也没有改变发布权限。
- 旧音频订阅异步完成或旧 UID 的离开事件可能晚于新连接；现在验证客户端和远端用户实例。视频 DOM 节点记录绑定的参与者，旧清理回调不能清空新人的画面，切换 UID 也不复用旧视频节点。

摄像头只能绑定到账号身份，无法根据人脸判断实际坐在设备前的人。截图对应课程仍需要使用真实参与者账号与设备复测。
