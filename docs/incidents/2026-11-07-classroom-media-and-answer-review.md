# 切窗黑屏、人员视频不同步、查看答案跳题与回放清晰度

日期：2026-11-07。依据：用户提供的 6.367 秒录屏、四张图片、当前工作区代码及本地回归验证。用户描述中的图号包含录屏，本文按问题名称对应。

本记录包含代码修复与本地回归验证；提交、推送不等于已经完成部署，线上状态需单独核实。录屏没有对应的浏览器控制台和 RTC 事件日志；《老挝合作》课程原始录像及 HLS 清单也尚未取得。因此，下文区分已确认的代码缺陷与历史现场仍需确认的触发条件。

## 1. 切换窗口时视频出现两轮黑屏

录屏约 0.5 秒已有共享画面，约 1–1.5 秒黑屏，约 2 秒恢复，约 3.5–4.5 秒再次黑屏，约 5 秒恢复。共享画面与多个人员视频同时消失，说明应优先排查共同的接收端生命周期。

已确认的代码路径：

1. `use-classroom-sync.tsx` 监听 `focus`、`pageshow`、`visibilitychange` 等事件，恢复前台时调度刷新。
2. `classroom-v3.tsx` 的恢复任务会调用 `renewClassroomCredentials()`，接着调用 `recoverMedia()`。
3. 原 `recoverMediaNow()` 即使连接仍然健康，也逐个退订、重新订阅所有远端视频及音频。
4. 页面恢复可见和窗口再次获得焦点可能分别触发任务。原来的 2 秒间隔限制不能阻止间隔更久的第二次重建；课堂开始及其他凭证更新也可能走同一路径。

这条路径可以解释录屏的全体视频一起黑屏、恢复后再次黑屏；没有现场事件日志，不能断言当时第二次任务具体由哪一种事件触发。

修复：普通续期、返回前台和课堂开始保留当前 SDK 用户对象上仍然有效的视频、音频订阅，只修复缺失或已结束的轨道。实际重连、断线重入、令牌失效后重入和手动重置仍完整恢复订阅，避免保留旧传输上的冻结轨道。

## 2. 不同端看到同一人员的视频状态不同

发现两条确实存在的恢复缺口：

- 摄像头小窗会请求低清小流。原代码只为共享屏幕处理小流不可用的情况；摄像头切流失败会直接跳过随后的视频订阅。发布端没有成功启用双流时，接收端可能持续显示头像或视频暂停状态。
- 订阅失败只写控制台，没有稳定的重试；若错过发布事件，人员的 `hasVideo` 状态也缺少与 SDK 当前用户列表的主动核对。刷新页面后重新入会，可能暂时恢复。

修复：摄像头和共享屏幕都在切流失败时继续使用现有或默认的高清流；同一发布周期内记住小流不可用状态，避免反复失败。通过 SDK 现有网络质量回调核对人员发布状态、重试缺失的视频订阅，保持其余视频正常播放。记录失败的 RTC UID 与目标流类型，便于现场定位。

SDK 文档明确说明切换远端大小流需要发布端启用双流，并列出浏览器限制：[Agora Web SDK 双流与切流接口](https://api-ref.agora.io/en/video-sdk/web/4.x/interfaces/iagorartcclient.html#setremotevideostreamtype)。

截图本身无法确定当次是切流失败、订阅失败，还是发布事件遗漏；没有将其中一种推测当作已经取得的线上日志结论。同账号不同设备各自的本地摄像头开关仍有独立含义，不强制把所有设备的开关合并。

## 3. 点击旧题“查看答案”却显示新题

已确认并复现：聊天卡片传入的旧题 ID 正确，但 `StudentQuestion` 里的自动跟题 effect 在发现另一道题处于作答中、当前题已结束时调用 `onFollowActive()`，清除手动选择。旧题详情尚未加载时也可能被该逻辑抢先切走。

修复：聊天卡片明确传递“回看”或“作答”意图。手动回看固定题目 ID，显示该题自己的已提交答案，结束后的答案保持只读；提供“返回当前题目”。手动打开正在作答的题目仍继续跟随后续新题，不会因修复历史回看而失去正常跟题行为。

## 4. 《老挝合作》回放模糊，以及手动选择高画质

当前实现有网速自适应，但需要区分三段链路：

| 环节 | 修改前行为 | 对模糊的影响 |
| --- | --- | --- |
| 直播发布端 | 摄像头高清通常为 720p；持续弱网时降到 360p，进一步降到 180p，并降低码率 | 录制前已经丢失的细节无法靠播放器恢复 |
| 录像合成 | 固定 1280×720、15 fps、1800 Kbps | 大屏或全屏观看时，细节受录制分辨率和码率限制 |
| 回放 | 优先 HLS，兼容性失败时使用 MP4；没有手动画质入口 | HLS 是传输格式；只有实际清单提供多个码率/分辨率时，才有可切换的自适应档位 |

这些是代码确认的限制，不能据此断言昨天第 7 课具体在哪一环节变糊。仍需读取那节课的原始 MP4、HLS 清单，以及录制期间发布端的实际发送分辨率、码率和丢包数据。仅凭一张播放截图不能判断当时是否发生了播放端自动降档。

本次改动：

- 保留默认“自动”；有原始 MP4 时增加“高画质（原始录像）”，显式选择后使用原片。
- 只有 HLS 源时，若清单提供多个实际档位，在支持 hls.js 的浏览器中可选择最高分辨率，分辨率相同时选择更高码率。
- 显示实际媒体高度，如 `720p`。单档源显示源画质，不虚构 1080p 档位。Safari 原生 HLS 且没有 MP4 备选时保留浏览器原生策略，不显示无法兑现的手动选项。
- 切换画质保留当前播放位置、暂停/播放状态；自动接续播放只在切换到新录像时触发，避免用户暂停后切画质又被强制播放。
- 新发起的录像合成配置提高到 1920×1080、15 fps、3500 Kbps。只影响新录像；实际细节仍取决于采集与上行源质量，文件大小和分发流量也会相应增加。

未增加转码流水线，因此没有宣称所有历史录像已经拥有 360p/720p/1080p 多档自适应。旧录像若源文件本身模糊，切换到“高画质”也不会凭空恢复细节。
